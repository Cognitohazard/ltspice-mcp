The `summary` recipe's `errors`, `warnings` and `meas_errors`, and the `severity` of each line it relays, now come from the run's classified diagnostics, the source of the run row's `diagnostics`, so the two no longer disagree about what the simulator said or how severe it called it. A condition is an error or a warning only where the simulator wrote that word on it. Its severity is the strongest word over its occurrences, and the summary lists the line that word was written on: LTspice XVII's failed operating point is the error `Fatal Error: … trouble with node "…"`, and a diagnostic whose severity comes from a later occurrence names it in a new `severity_text`. Each list holds one entry per condition, as `diagnostics` counts it. A line with no such word is in neither list and stays in `diagnostics`: LTspice's bias-point stepping rungs and its iteration limit, LTspice 26's failed operating point and its `file(N): …` deck messages (including one for a `.meas` it cannot read, which no longer gives a `meas_errors` entry), and ngspice's `Note:` lines. A relayed line with no word of the simulator's own carries no `severity`, where it used to say `error`. An error that names a `.meas` is relayed once, as that measurement, and no `meas_batch_abort` is claimed for a log that holds a measurement. For QSPICE and Xyce, whose log wording the server has no recordings of, the run row's `diagnostics` now tell apart a line the simulator starts with `Error:` or `Warning:`, and the summary lists those; other wordings of an error are counted as unclassified. A `.meas` ngspice skips in batch mode is still reported as skipped, read from a new `measurement_skipped_batch` condition; its notice is no longer in `warnings`.
