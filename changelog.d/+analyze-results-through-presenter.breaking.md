`analyze_results` evaluates every recipe it is asked for in one call and sends its answer through the same reply layer as `verify_circuit`, `run_experiments` and `jobs`. A reply too long for its target is stored whole and its lists cut, each named in `cut` with the cursor that reads the rest; `continue` (or `include.per_run.cursor`) with that cursor reads a page sliced from the stored answer, so nothing is evaluated again and a page is never refused or emptied because a source changed: it carries the snapshot of the sources it was computed from. A cursor lasts as long as the stored answer (`[analysis] result_set_ttl_hours`), and a cursor from an earlier release is refused with the way to start again. A budget no longer drops what the request asked to include (provenance, outliers, the list of signals) and no longer reports `budget_truncated`; `reduced` and a spec's counts are never cut. With no target a reply still holds at most a `per_run` page's `limit` and 100 rows of each other list, said through `cut`. Rows left out that carry a fact are named in the new `rows_not_shown`, with a cursor at each, an observation lifted from a recipe's rows names at most three of them, with `row_count` and each row's `index` (and a cursor when the rows are cut), or only `every_row` when every row carries it, and an inline waveform too long for the reply is drawn at fewer points, never below 32, its `cut` entry saying how many. The analysis attached to a run is the answer `analyze_results` gives for the same request over the finished job: the receipt presents it beside its run rows under one target, cut with a cursor `analyze_results` reads, and no longer says `budget_truncated` or `budget_not_met` about it. A job recorded by an earlier release keeps its attached analysis in a shape this release does not render; run `analyze_results` over the job instead.
